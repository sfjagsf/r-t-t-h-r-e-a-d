# 26. 设备框架头文件：通用设备对象与接口

> 对应源码：
>
> - `include/rtdef.h`：通用设备对象、类别、标志和接口表的**定义**；
> - `include/rtthread.h`：通用 `rt_device_*()` API 的**声明**；
> - `components/drivers/include/rtdevice.h`：按配置包含各类专用驱动头文件的**总入口**；
> - `components/drivers/core/device.c`：上述通用 API 的实现，本节暂不逐函数展开。

## 1. 先分清三个头文件的职责

不要把名字相近的三个头文件混为一处：

```text
rtdef.h
  └─ 定义“设备对象应有什么字段、设备接口长什么样”

rtthread.h
  └─ 声明“外部如何调用设备框架”
     例如 rt_device_find/open/read/write/control

rtdevice.h
  └─ 驱动子系统总入口；按 RT_USING_SERIAL、RT_USING_SPI 等宏
     包含对应类别的专用头文件
```

源码锚点：`rtdevice.h` 开头先包含 `rtdef.h`、`rtthread.h`、`drivers/core/driver.h`、`drivers/core/bus.h`，随后依据大量 `RT_USING_*` 宏选择性包含 `dev_serial.h`、`dev_i2c.h`、`adc.h`、`dev_pwm.h` 等。它是“聚合入口”，不是 `struct rt_device` 的定义地点。

## 2. 总体运行模型：对象、接口、驱动实现

```text
应用/组件
  │ rt_device_open/read/write/control
  ▼
设备框架（device.c）
  │ 从 dev 取得统一接口表 dev->ops
  ▼
具体驱动（UART、SPI、ADC、Flash、网卡……）
  │ 寄存器、DMA、缓冲区、硬件中断
  ▼
硬件
```

设备框架的契约是：

```text
框架规定：设备对象的共同字段，以及 init/open/read/write 等操作的函数原型。
驱动负责：填写该设备实际支持的回调，并处理自己的硬件细节。
```

因此上层不必为 UART、SD 卡、ADC 分别学习一套“查找/打开/关闭”的管理方式；差异主要藏在具体驱动的回调内。

## 3. `RT_USING_DEVICE`：设备组件的总开关

设备定义被包在：

```c
#ifdef RT_USING_DEVICE
    /* device object and API declarations */
#endif
```

```text
未定义 RT_USING_DEVICE
  → 不编译通用设备框架；也没有 struct rt_device

定义 RT_USING_DEVICE
  → 可以注册、查找和统一访问设备对象
```

这是 RT-Thread 按需裁剪的体现：不需要设备模型的小型工程不必为设备对象、接口表、注册逻辑支付 ROM/RAM 成本。

## 4. 两种“类型”：对象类型与设备类别

设备对象同时有两层类型信息：

```text
dev->parent.type
  = RT_Object_Class_Device
  问题：它属于内核对象系统中的哪一大类？
  用途：对象总链表、rt_object_find()、rt_device_find()

dev->type
  = RT_Device_Class_Char / Block / ADC / ...
  问题：它在功能上属于哪一种设备？
  用途：语义分类、专用组件匹配、调试和管理
```

例如 UART 通常是：

```text
父对象类型：RT_Object_Class_Device
设备功能类别：RT_Device_Class_Char
```

`RT_Object_Class_Device` 不等于 `RT_Device_Class_Char`。前者是“设备对象”，后者是“字符设备”。

## 5. `enum rt_device_class_type`：功能类别而不是调度状态

```c
enum rt_device_class_type
{
    RT_Device_Class_Char = 0,
    RT_Device_Class_Block,
    RT_Device_Class_NetIf,
    ...
    RT_Device_Class_Unknown
};
```

只有第一项显式赋值为 0；后续枚举值依次加 1。业务代码应使用枚举名，而不是依赖具体数值。

| 类别 | 典型对象 | 主要语义 |
|---|---|---|
| `Char` | UART、终端、虚拟串口 | 连续字节流 |
| `Block` | SD 卡、eMMC、磁盘 | 固定块/扇区读写 |
| `NetIf` | 以太网 MAC、Wi-Fi 网卡 | 网络帧接口 |
| `MTD` | 原始 NOR/NAND Flash | 擦除块、页、坏块等原始存储特性 |
| `CAN` | CAN 控制器 | CAN 帧收发 |
| `RTC` | 芯内/外置实时时钟 | 年月日时分秒，不是内核 Tick |
| `Sound` / `Graphic` | 音频、LCD/帧缓冲 | 多媒体数据接口 |
| `I2CBUS` / `SPIBUS` | I2C/SPI 控制器 | 总线本身 |
| `SPIDevice` | 挂在 SPI 上的 Flash、IMU、LCD | 总线上的具体从设备 |
| `USBDevice` / `USBHost` / `USBOTG` | USB 从机/主机/双角色控制器 | USB 角色区别 |
| `SDIO` | SDIO 控制器 | SD/SDIO 总线接口 |
| `Timer` | MCU 的 TIMx 等硬件定时器 | 不等于 `struct rt_timer` 软件定时器 |
| `Sensor` / `Touch` / `PHY` / `WLAN` | 传感器、触摸、以太网 PHY、Wi-Fi | 专用设备框架类别 |
| `Pin` / `ADC` / `DAC` / `WDT` / `PWM` | MCU 常用外设 | 各自专用控制语义 |
| `Bus` | 泛化总线对象 | 设备管理器使用的总线抽象 |
| `Unknown` | 暂未细分的设备 | 保底分类 |

重要边界：`dev->type` 不负责决定调用哪个函数。真正的多态调用由 `dev->ops` 决定；`type` 提供的是分类语义。

## 6. 指针别名：`rt_device_t`

源码：

```c
typedef struct rt_device *rt_device_t;
```

因此下面两种写法等价：

```c
rt_device_t dev;
struct rt_device *dev;
```

这只是 `typedef` 起的别名，没有创建新对象，也没有把“结构体指针变成另一个对象”。RT-Thread 用它让 API 参数更短、更符合设备抽象名称。

## 7. `struct rt_device_ops`：统一行为接口表

启用 `RT_USING_DEVICE_OPS` 时：

```c
struct rt_device_ops
{
    rt_err_t   (*init)   (rt_device_t dev);
    rt_err_t   (*open)   (rt_device_t dev, rt_uint16_t oflag);
    rt_err_t   (*close)  (rt_device_t dev);
    rt_ssize_t (*read)   (rt_device_t dev, rt_off_t pos,
                          void *buffer, rt_size_t size);
    rt_ssize_t (*write)  (rt_device_t dev, rt_off_t pos,
                          const void *buffer, rt_size_t size);
    rt_err_t   (*control)(rt_device_t dev, int cmd, void *args);
};
```

它不是“某个设备实例的数据”，而是一张行为表。典型串口驱动会定义：

```c
static const struct rt_device_ops uart_ops =
{
    .init    = uart_init,
    .open    = uart_open,
    .close   = uart_close,
    .read    = uart_read,
    .write   = uart_write,
    .control = uart_control,
};
```

再让设备对象指向它：

```c
uart1.parent.ops = &uart_ops;
```

调用链：

```text
rt_device_read(&uart1.parent, 0, buf, n)
    ↓
device.c 检查设备状态
    ↓
uart1.parent.ops->read(&uart1.parent, 0, buf, n)
    ↓
uart_read() 操作 UART 私有缓冲区、DMA 或寄存器
```

这是 C 中“接口表实现多态”的核心：同一个 `rt_device_read()`，可以转发至 `uart_read`、`sd_read`、`adc_read` 等不同实现。

### 为什么把回调放到独立 `ops` 表

```text
对象实例：保存状态
  flag、open_flag、ref_count、私有指针……

ops 表：保存行为
  init/open/read/write/control 函数地址
```

多个同型号设备可共用同一张 `static const` 接口表：

```text
uart0 ─┐
uart1 ─┼─> uart_ops（只读，通常可放在 Flash）
uart2 ─┘
```

相比每个实例各存 6 个函数指针，这通常更节省 RAM，也不容易被运行时误改。

### 不启用 `RT_USING_DEVICE_OPS` 时

六个函数指针直接放在 `struct rt_device` 中。`device.c` 通过宏统一两种布局：

```c
#ifdef RT_USING_DEVICE_OPS
#define device_read (dev->ops ? dev->ops->read : RT_NULL)
#else
#define device_read (dev->read)
#endif
```

所以后续的框架代码不需要因为结构体布局不同写两套 `rt_device_read()`。

## 8. 六个通用操作的职责边界

| 回调 | 职责 | 不应承担的职责 |
|---|---|---|
| `init` | 一次性准备硬件/软件资源 | 每次打开时的模式配置 |
| `open` | 按本次 `oflag` 配置使用模式 | 创建对象或登记设备名 |
| `close` | 最后一个使用者离开时收尾 | 释放静态设备对象本身 |
| `read` | 从设备或驱动缓冲区取数据 | 通用对象查找 |
| `write` | 向设备或发送缓冲区提交数据 | 设备注册 |
| `control` | 设备特有控制命令 | 取代所有通用读写操作 |

`init/open/close` 的区分很重要：

```text
register：纳入内核设备对象系统
init：准备硬件，通常只成功一次
open：本次使用者以何种方式启用设备
close：最后一个打开者离开时收尾
destroy/unregister：设备对象生命周期结束
```

## 9. `struct rt_device`：设备对象完整骨架

简化的最小布局：

```c
struct rt_device
{
    struct rt_object parent;

    enum rt_device_class_type type;
    rt_uint16_t flag;
    rt_uint16_t open_flag;
    rt_uint8_t ref_count;
    rt_uint8_t device_id;

    rt_err_t (*rx_indicate)(rt_device_t dev, rt_size_t size);
    rt_err_t (*tx_complete)(rt_device_t dev, void *buffer);

    const struct rt_device_ops *ops; /* 开启 DEVICE_OPS 时 */
    rt_err_t (*readlink)(rt_device_t dev, char *buf, int len);
    void *user_data;
};
```

实际布局会随 `RT_USING_DM`、`RT_USING_POSIX_DEVIO` 等宏扩展；不能把不同配置下 `sizeof(struct rt_device)` 当成固定值。

### 9.1 `parent`：对象身份和设备总链表节点

```c
struct rt_object parent;
```

具体设备对象包含 `rt_device`，`rt_device` 再包含 `rt_object`：

```text
具体 UART 对象
  └─ struct rt_device
       └─ struct rt_object parent
```

不是 `rt_object` 包含 UART/SPI/ADC。相反，具体对象在开头嵌入基础对象部分，借此复用名字、对象类型、静态/动态属性和同类对象总链表。

注册时的源码锚点：

```c
rt_object_init(&(dev->parent), RT_Object_Class_Device, name);
```

该调用将 `parent.list` 挂入 `RT_Object_Class_Device` 对应的对象总链表，因此 `rt_device_find("uart1")` 可以复用 `rt_object_find()` 按名称查询。

### 9.2 `type`：设备功能类别

```c
enum rt_device_class_type type;
```

它是第 5 节中的设备类别。它不取代 `parent.type`，也不存放线程状态、设备打开状态。

### 9.3 `flag`：能力与硬件运行状态位图

```c
rt_uint16_t flag;
```

主要宏：

```c
RT_DEVICE_FLAG_RDONLY / WRONLY / RDWR
RT_DEVICE_FLAG_REMOVABLE / STANDALONE / STREAM
RT_DEVICE_FLAG_ACTIVATED / SUSPENDED / DYNAMIC
RT_DEVICE_FLAG_INT_RX / DMA_RX / INT_TX / DMA_TX
```

其中 `RDONLY=0x001`、`WRONLY=0x002`、`RDWR=0x003` 构成访问能力组合；`ACTIVATED=0x010` 代表底层初始化已完成。

```text
flag = 设备能做什么 + 当前硬件大状态
```

优点是节省字段、位测试快；代价是“能力”和“运行状态”混在一个位图中，阅读时必须看清具体位的语义。

### 9.4 `open_flag`：当前打开方式

```c
rt_uint16_t open_flag;
```

```c
RT_DEVICE_OFLAG_CLOSE  0x000
RT_DEVICE_OFLAG_RDONLY 0x001
RT_DEVICE_OFLAG_WRONLY 0x002
RT_DEVICE_OFLAG_RDWR   0x003
RT_DEVICE_OFLAG_OPEN   0x008
RT_DEVICE_OFLAG_MASK   0xf0f
```

```text
flag      ：设备固有能力与运行状态
open_flag ：当前是否已打开、以何方式打开
```

例如设备可能支持读写：

```c
dev->flag = RT_DEVICE_FLAG_RDWR;
```

但尚未被任何人打开：

```c
dev->open_flag = RT_DEVICE_OFLAG_CLOSE;
```

第一次以读写方式打开成功后，大意为：

```text
open_flag = RT_DEVICE_OFLAG_OPEN | RT_DEVICE_OFLAG_RDWR
```

`RT_DEVICE_OFLAG_MASK` 用于比较旧的打开模式与新的请求模式；它保留访问位及预留扩展位，而不只是判断 OPEN 这一位。

### 9.5 `ref_count`：打开引用计数

```c
rt_uint8_t ref_count;
```

```text
第一次 open 成功：ref_count = 1
第二次 open 成功：ref_count = 2
一次 close：        ref_count = 1，硬件仍不关闭
最后一次 close：    ref_count = 0，才进入底层 close
```

它记录的是“成功 `open()`、尚未配对 `close()` 的次数”，不是精确的线程数量。其目的在于避免一个模块关闭设备时，误伤仍在使用该设备的其他模块。字段只有 8 位，框架在递增后用断言检测从 255 回绕至 0 的错误。

### 9.6 `device_id` 与可选 `master_id`

```c
rt_uint8_t device_id;
```

它是辅助编号，可供设备管理器或具体驱动使用；面向用户的主要身份仍是 `parent.name`。启用设备管理器时还有 `master_id`，用于扩展的主控/管理关系。

### 9.7 `user_data`：通用私有数据挂载点

```c
void *user_data;
```

可将某份驱动私有上下文挂到通用设备对象：

```c
dev->user_data = &private_context;
```

优点是灵活；代价是 `void *` 无编译期类型检查。确定的驱动更常见的方式是定义一个更大的结构体，将 `struct rt_device` 嵌入其中。

### 9.8 `readlink`

```c
rt_err_t (*readlink)(rt_device_t dev, char *buf, int len);
```

这是为动态设备和文件系统链接语义预留的可选回调；它不是普通 `read()` 的替代品。

## 10. 反向回调：设备通知上层，而非上层调用设备

```c
rt_err_t (*rx_indicate)(rt_device_t dev, rt_size_t size);
rt_err_t (*tx_complete)(rt_device_t dev, void *buffer);
```

它们与 `ops` 的方向相反：

```text
正向接口（上层 → 设备）：
rt_device_read() → dev->ops->read()

反向通知（设备 → 上层）：
接收中断/DMA 完成 → dev->rx_indicate()
发送完成中断/DMA 完成 → dev->tx_complete()
```

典型接收路径：

```text
UART 接收中断
  ↓
驱动把数据放进驱动缓冲区
  ↓
dev->rx_indicate(dev, 可读取数据量)
  ↓
上层唤醒读取线程或释放信号量
  ↓
线程再调用 rt_device_read()
```

使用回调而不是持续轮询，可避免线程反复询问“有没有数据”。但该回调可能由中断上下文触发，通常应短小，不应做会阻塞的工作。

`device.c` 中对应的 setter 只做保存：

```c
dev->rx_indicate = rx_ind;
dev->tx_complete = tx_done;
```

真正何时调用它们，取决于具体 UART/CAN/网卡等驱动的中断或 DMA 完成路径。

## 11. `control(cmd, args)`：避免统一接口无限膨胀

六个通用回调无法描述所有硬件功能，例如 UART 配波特率、PWM 配占空比、Flash 擦除、ADC 设置采样参数。

因此统一保留：

```c
rt_err_t (*control)(rt_device_t dev, int cmd, void *args);
```

通用命令位于较低编号：

```c
RT_DEVICE_CTRL_RESUME
RT_DEVICE_CTRL_SUSPEND
RT_DEVICE_CTRL_CONFIG
RT_DEVICE_CTRL_CLOSE
RT_DEVICE_CTRL_SET_INT
RT_DEVICE_CTRL_CLR_INT
```

类别专用命令可通过：

```c
#define RT_DEVICE_CTRL_BASE(Type) \
    ((RT_Device_Class_##Type + 1) * 0x100)
```

构造自己的命令段。例如 RTC 的专用命令可从 `RT_DEVICE_CTRL_BASE(RTC)` 之后取值，减少与 ADC/PWM/CAN 命令碰撞的风险。

设计取舍：

```text
优点：统一 API 小而稳定；专用功能可扩展。
代价：cmd 与 args 的类型主要依靠驱动文档和约定保证，编译器无法完全检查。
```

## 12. `struct rt_wqueue` 与 POSIX 设备 I/O 扩展

```c
struct rt_wqueue
{
    rt_uint32_t flag;
    rt_list_t waiting_list;
    struct rt_spinlock spinlock;
};
```

启用 `RT_USING_POSIX_DEVIO` 后，每个 `rt_device` 额外包含：

```c
const struct dfs_file_ops *fops;
struct rt_wqueue wait_queue;
```

用途是支持接近 POSIX 的：

```text
open("/dev/uart1", ...)
read(fd, ...)
poll()/select() 等待设备可读、可写或发生事件
```

`wait_queue` 中保存等待事件的线程链表，并用自旋锁保护。这不是普通 `rt_device_read()` 必需的字段；宏关闭时每个设备不会为它额外占 RAM。

## 13. `RT_USING_DM`：设备管理器扩展

启用设备管理器后，`struct rt_device` 会增加：

```c
struct rt_bus *bus;
rt_list_t node;
struct rt_driver *drv;
```

表示：

```text
bus：当前设备挂在哪条总线
node：当前设备挂入 bus 的链表节点
drv：当前与该设备绑定的驱动
```

关系从简单的“名称注册”扩展成：

```text
总线 bus
  └─ 设备 device
       └─ 驱动 driver
```

此模式适合 SPI、I2C、PCI、USB 等有枚举和驱动匹配需求的复杂系统。继续启用 `RT_USING_OFW`、`RT_USING_DMA`、`RT_USING_DVFS` 时，还会增加设备树节点、DMA 操作和动态调频相关字段。它们均是可选的，未开启时不进入对象布局。

## 14. `struct rt_device_notify`

头文件末尾还有：

```c
struct rt_device_notify
{
    void (*notify)(rt_device_t dev);
    struct rt_device *dev;
};
```

它把“通知函数 + 被通知的设备”封装成一个小对象，方便异步通知或设备管理相关代码传递。它不是每个 `rt_device` 内嵌的成员，也不是 `rx_indicate` 的替代品。

## 15. 通用 API 的声明位置：`rtthread.h`

在当前源码版本中，以下声明位于 `include/rtthread.h`：

```c
rt_device_t rt_device_find(const char *name);
rt_err_t rt_device_register(rt_device_t dev, const char *name,
                            rt_uint16_t flags);
rt_err_t rt_device_unregister(rt_device_t dev);
rt_err_t rt_device_init(rt_device_t dev);
rt_err_t rt_device_open(rt_device_t dev, rt_uint16_t oflag);
rt_err_t rt_device_close(rt_device_t dev);
rt_ssize_t rt_device_read(rt_device_t dev, rt_off_t pos,
                          void *buffer, rt_size_t size);
rt_ssize_t rt_device_write(rt_device_t dev, rt_off_t pos,
                           const void *buffer, rt_size_t size);
rt_err_t rt_device_control(rt_device_t dev, int cmd, void *arg);
```

它们形成应用/组件面向设备框架的统一入口。

## 16. 一个完整的对象 + 接口例子

```c
struct my_uart
{
    struct rt_device parent;
    volatile void *regs;
    void *rx_buffer;
};

static const struct rt_device_ops my_uart_ops =
{
    .init  = my_uart_init,
    .open  = my_uart_open,
    .read  = my_uart_read,
    .write = my_uart_write,
};
```

```text
对象：my_uart（包含通用 rt_device 与 UART 私有状态）
接口：my_uart_ops（把统一动作映射至 UART 实现）
组件：RT_USING_DEVICE 设备框架（注册、查找、打开、转发调用）
```

注册和使用的逻辑链：

```text
驱动填写 uart.parent.ops = &my_uart_ops
  ↓
rt_device_register(&uart.parent, "uart1", flags)
  ↓
rt_device_find("uart1")
  ↓
rt_device_open(dev, oflag)
  ↓
rt_device_write(dev, 0, data, size)
  ↓
dev->ops->write(...) → my_uart_write(...)
```

## 17. 本节结论

1. `rtdef.h` 定义设备对象和接口表；`rtthread.h` 声明通用 API；`rtdevice.h` 是专用驱动头的配置化聚合入口；
2. `rt_object` 不包含各种设备；具体设备对象通过 `rt_device` 在开头嵌入 `rt_object`；
3. `parent.type` 是内核对象类别，`dev->type` 是设备功能类别，二者必须区分；
4. `ops` 表是设备行为接口，`rt_device_*()` 是框架入口，具体驱动是最终实现；
5. `flag` 描述能力和硬件状态，`open_flag` 描述当前打开方式，`ref_count` 管理打开引用；
6. `rx_indicate/tx_complete` 是设备到上层的反向事件通知，不是上层调用设备的接口；
7. `RT_USING_DEVICE`、`RT_USING_DEVICE_OPS`、`RT_USING_POSIX_DEVIO`、`RT_USING_DM` 等宏让设备框架可从小型 MCU 配置逐步扩展。
